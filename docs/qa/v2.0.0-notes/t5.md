## Findings

- F1 (stage 1, attribution): both memguard kills (12:49:25 pid 52432, 12:58:08 pid 27928) hit processes named server.test.exe with no path recorded. The 12:58:08 kill provably was not this repo's: my isolated run started 12:59:46.6, 98s later. A foreign, still-running mutation gate over caro-ai-pvp's own internal/server has been spawning name-identical server.test.exe processes all through the window: `make mutate-full LABEL=server-regate ARGS="-pkgs internal/server"` -> `go run ./cmd/mutate -allow .mutate-allow -parallel 6 -pkgs internal/server -resume logs/archive/mutate-server-regate.log` (PIDs 31672/8624, live at 13:0x; quotes-manager has no cmd/mutate and no logs/archive, and the caro repo log exists at C:\Users\lavantien\dev\github\caro-ai-pvp\logs\archive\mutate-server-regate.log). That gate shows no GOMEMLIMIT on its command line, unlike this repo's tools/mutator recipe. The 12:49:25 pid stays formally ambiguous (my internal/server binary and the foreign gate were both live), but the only clean experiment says this repo's server suite is green and lean in isolation, so the external gate is the consistent single root cause for both breaches and for the system-critical reap that killed attempt 1. No quotes-manager package failure was observed anywhere: 0 fail events in the full 1 MB JSON capture.
- F2 (environmental, blocks stage-1 completion): baselines on this box are contaminated while the foreign gate runs. memcapmon matches by process name across repos (go.exe, make.exe, *.test.exe, regex in memguard.log header), so a foreign 17-18 GB balloon both consumes the shared 16 GB cap and drives the box critical, which reaps harness background tasks (attempt 1 died exactly that way). Options for main: rerun stage 1 while the foreign gate is idle, or tighten the memguard match to repo-origin executables. Secondary protocol gap observed: plain `make test` carries no jobwrap (the Makefile documents the hazard for WRAP targets), so a reaped wrapper strands its test binaries as orphans until memguard or a sweep finishes them.
- Answer to main's 12:58 question: neither option. The isolated run had not started at 12:58:08 (start marker 12:59:46.6) and it completed with no in-flight test at all. TestRestoreRejectsBadVersion was in flight only in attempt 1's JSON at the 12:48:04 output stop; its body is a 15-byte POST expecting 400 through a 10 MiB-capped handler (handlers_backup.go:32-48), it predates T4's chain (0916c0e), and the surrounding suite is green in isolation, so it is not incriminated.
